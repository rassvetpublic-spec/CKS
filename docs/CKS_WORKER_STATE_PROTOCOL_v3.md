# Протокол состояния воркера CKS v3 (CKS Worker State Protocol v3)

## Назначение (Purpose)

Протокол **CKS Worker State Protocol v3** определяет детерминированные состояния выполнения, модель жизненного цикла, инварианты переходов и правила отчётности воркера (`Worker`) в системе CKS.

Протокол обеспечивает безопасную работу воркеров в распределённой среде под управлением KAT9I_OS и Antigravity с гарантией целостности канона знаний и предотвращением галлюцинаций (Anti-Poisoning).

---

## Границы ответственности (Boundaries)

- **CKS (Knowledge & Canon Layer):**
  - хранилище канонических спецификаций и схем;
  - контекст и намерения (`Intent`);
  - реестры доказательств (`Evidence`);
  - протоколы решений (`Decision Records`);
  - неизменяемая история изменений (`History`).
- **KAT9I_OS & Antigravity (Execution & Runtime Layer):**
  - среда выполнения и 4 изолированных профиля исполнения (`Worker Profiles`);
  - оркестрация задач и распределённая очередь;
  - инструменты и вызовы моделей;
  - физическое размещение данных: **100% данных и конфигураций располагаются строго внутри `C:\GIT\`** (через архитектуру NTFS Junctions: `~/.gemini` ➔ `C:\GIT\.gemini\`, `~/.kat9i` ➔ `C:\GIT\.kat9i\`).

Воркер исполнения никогда не управляет каноном напрямую и не заменяет независимый QA-контроллер.

---

## Модель состояний воркера (State Machine Model)

```text
       [DISCOVERED]  (Задача найдена по критерию '## Задание для Worker')
             ↓
         [CLAIMED]    (Захват задачи: фиксация Worker identity, таймстемпа и канала)
             ↓
        [PREPARING]   (Создание рабочей ветки, изоляция контекста, валидация SSoT)
             ↓
         [RUNNING]    (Исполнение задачи в ветке, генерация артефактов)
             ↓
       [DISTILLING]   (Формирование distillate_object_v1 и отчёта WORKER_REPORT v1)
             ↓
       [WAITING_QA]   (Публикация PR, передача контроллеру QA, 0 LLM-токенов в ожидании)
        ╱         ╲
       ↓           ↓
    [DONE]      [BLOCKED]
  (QA PASS)   (QA FAIL / Нарушение инвариантов)
```

## Описание состояний (State Specifications)

### 1. `DISCOVERED` (Обнаружено)
- **Условие входа:** Задача найдена через мониторинг событий (`github_api_poller` / Spy Worker) по сигнатуре `## Задание для Worker` при отсутствии назначенного исполнителя (`assignees == []`).
- **Действие:** Проверка наличия целевого репозитория, описания цели и канала обратной связи (`CHANNEL`).
- **Запрет:** Запрещено начинать модификацию кода до фиксации захвата задачи.

### 2. `CLAIMED` (Захвачено)
- **Условие входа:** Воркер публикует декларацию захвата (`CLAIMED:`) в целевом канале задачи.
- **Формат декларации:**
  ```text
  CLAIMED:
  Worker: <Worker_ID>
  Repository: https://github.com/rassvetpublic-spec/CKS
  Task: #<Issue_ID> (<Title>)
  Started: <ISO_8601_Timestamp>
  Channel: <Issue_URL / PR_URL>
  Return Format: WORKER_REPORT v1
  ```
- **Назначение:** Предотвращение гонки и дублирования работы между несколькими воркерами.

### 3. `PREPARING` (Подготовка)
- **Условие входа:** Успешная фиксация `CLAIMED`.
- **Действие:** Создание изолированной ветки (`feature/issue-<ID>-...`), проверка чистоты рабочего дерева, валидация базовых тестов и схем.
- **Инвариант:** Прямая работа в ветке `main` категорически запрещена.

### 4. `RUNNING` (Исполнение)
- **Условие входа:** Ветка создана, окружение валидно.
- **Действие:** Выполнение содержательной работы (разработка спецификаций, кода, тестов).
- **Инвариант:** Воркер вносит изменения только в пределах выданного задания (`Scope Bound`).

### 5. `DISTILLING` (Дистилляция знаний)
- **Условие входа:** Изменения подготовлены, локальные тесты пройдены.
- **Действие:** В соответствии с **ADR-0001**, воркер генерирует машиночитаемый дистиллят (`distillate_object_v1`) и формирует отчёт `WORKER_REPORT v1`.
- **Инвариант:** В канон передаётся кристаллизованный результат, а не сырой лог диалога LLM.

### 6. `WAITING_QA` (Ожидание проверки)
- **Условие входа:** Создан Pull Request, отправлено уведомление в целевой канал задачи.
- **Действие:** Переход в режим пассивного ожидания вердикта от независимого QA-контроллера (`WORKER QA`).
- **Инвариант токенов:** В режиме ожидания вызовы LLM запрещены (**0 LLM tokens**). Опрос статуса выполняется детерминированным скриптом каждые 10 секунд.
- **Разделение ролей:** Автор изменения не имеет права проводить QA собственного PR.

### 7. `DONE` (Завершено)
- **Условие входа:** Получен вердикт `QA PASS` от независимого аудитора на точный коммит (`Exact HEAD SHA`).
- **Действие:** Разрешение на слияние PR в основную ветку и фиксация в истории CKS.

### 8. `BLOCKED` (Заблокировано)
- **Условие входа:** Любой сбой проверки (провал CI, нарушение схемы, вердикт `QA FAIL` или несоответствие границ доверия).
- **Действие:** Принцип **Fail-Closed STOP**. Воркер публикует отчёт с описанием блокирующих факторов (`blockers`) и ожидает вмешательства оператора.

### 9. `ABORTED` (Прервано)
- **Условие входа:** Отмена задачи координатором, конфликт версий или превышение лимитов исполнения.
- **Действие:** Очистка временных артефактов, освобождение слота присутствия.

## Инварианты переходов состояний (Transition Invariants)

1. **Инвариант независимости QA (Anti-Poisoning Law):**
   Ни один артефакт не может перейти из `RUNNING` напрямую в `DONE`. Переход в `DONE` возможен исключительно через `WAITING_QA` и независимый вердикт контроллера.
2. **Инвариант точного коммита (Exact SHA Boundary):**
   Вердикт QA действителен только для конкретного `commit_id`. Любое добавление коммита аннулирует предыдущий вердикт и возвращает статус в `WAITING_QA`.
3. **Инвариант обязательного возвратного канала (Return Channel Rule):**
   Каждая задача обязана иметь явный `CHANNEL`. Результаты возвращаются в обсуждение связанного Issue/PR.
4. **Инвариант физической границы (Strict Boundary Law):**
   Все локальные копии, временные файлы и логи воркера физически размещаются строго внутри `C:\GIT\`.
5. **Инвариант нулевого расхода в ожидании (Zero Token Wait):**
   Ожидание внешних событий не должно расходовать контекст нейросети.

## Машинный контракт переходов (State Machine Contract)

```yaml
schema_name: cks_worker_state_protocol_v3
version: "3.0"
valid_states:
  - DISCOVERED
  - CLAIMED
  - PREPARING
  - RUNNING
  - DISTILLING
  - WAITING_QA
  - DONE
  - BLOCKED
  - ABORTED

terminal_states:
  - DONE
  - BLOCKED
  - ABORTED

allowed_transitions:
  DISCOVERED: [CLAIMED, ABORTED]
  CLAIMED: [PREPARING, ABORTED]
  PREPARING: [RUNNING, BLOCKED, ABORTED]
  RUNNING: [DISTILLING, BLOCKED, ABORTED]
  DISTILLING: [WAITING_QA, BLOCKED]
  WAITING_QA: [DONE, BLOCKED, RUNNING, ABORTED]
  BLOCKED: [CLAIMED, ABORTED]
  DONE: []
  ABORTED: []

constraints:
  qa_independence: true
  zero_token_idle: true
  exact_sha_pinning: true
  require_return_channel: true
  storage_boundary: "C:\\GIT\\"
```

## Совместимость (Compatibility)

- **Версия контракта CKS:** `v3`
- **Совместимость с KAT9I_OS:** Полная (поддержка `WORKER_QA.md` и ролей `WORKER_SYNC`, `WORKER_CLASSIFICATION`)
- **Формат отчётов:** `WORKER_REPORT v1` (машинный YAML + Human View)
- **Контракт дистилляции:** `distillate_object_v1.yaml`
- **Протокол хендоффа:** `CKS_ASYNC_HANDOFF_PROTOCOL_v1.2`
