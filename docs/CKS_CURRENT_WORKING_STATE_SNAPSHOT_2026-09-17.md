# CKS — текущий рабочий снимок состояния

**Дата:** 17.09.2026  
**Назначение:** постоянная русская фиксация фактически реализованного рабочего слоя CKS.  
**Статус документа:** рабочий Snapshot (снимок), не Canon и не архитектурное Decision (решение).

## 1. Как читать версии CKS

В репозитории одновременно существуют два уровня, и это не ошибка само по себе.

### Замороженный базовый Core

`README.md` и `ARCHITECTURE.md` описывают архитектурный baseline `CKS_v1.2`:

- `architecture: stable`;
- `core: frozen`;
- развитие только через `GAP → Evidence → Proposal → Decision → Minimal Change`;
- Proposal не является Decision;
- Experiment не является Canon.

### Текущий развиваемый рабочий слой

`control/system-state.yaml` фиксирует:

- `current_version: CKS_v1.5`;
- baseline: `CKS_v1.2`;
- operational: `CKS_v1.3`;
- runtime: `CKS_v1.4`;
- development: `CKS_v1.5`;
- `core: frozen`;
- `runtime: evolving`;
- `experiments: isolated`.

Следовательно, `v1.5` не означает, что замороженный Core v1.2 был молча переписан. Это обозначение текущего состояния развиваемого рабочего слоя вокруг frozen baseline.

## 2. Граница системы

CKS отвечает за:

- контекст;
- знания;
- доказательства;
- решения;
- происхождение знаний;
- граф связей;
- историю изменений;
- представления знаний;
- самопроверку качества и архитектурных ограничений.

CKS не является исполнительной системой. KAT9I_OS остаётся слоем исполнения, рабочих процессов и операционных действий.

## 3. Знание-центричная модель

Основной рабочий объект — объект знания, а Project рассматривается как проекция графа знаний, а не как контейнер файлов.

Единая модель поддерживает:

- тип объекта;
- версию;
- статус развития;
- кластеры;
- теги;
- Projects-проекции;
- связи;
- доказательства;
- историю;
- сигналы уверенности, новизны, неопределённости и важности;
- интуитивные сигналы, которые не являются Decision;
- Obsidian-метаданные.

## 4. Жизненный цикл знания

Рабочая модель поддерживает расширенную цепочку статусов:

`raw → captured → normalized → deduplicated → clustered → researched → understood → connected → validated → knowledge → canonical → evolving → disputed → superseded → archived / rejected`.

Переход в `canonical` защищён требованиями к Evidence (доказательству) и Decision (решению). Аналитика, CI и Obsidian не могут самостоятельно превратить объект в Canon.

## 5. Рабочий граф знаний

`tools/cks_knowledge_graph_runtime.py` реализует:

- узлы;
- типизированные связи;
- зависимости;
- проверку битых ссылок;
- транзитивный обход зависимостей;
- JSON save/load;
- `schema_version: 2.0`;
- стабильные ID связей;
- версии связей;
- локальную историю связи;
- глобальный Relation History (историю связей);
- миграцию формата `1.0 → 2.0`;
- recovery snapshot (снимок восстановления);
- SHA-256-проверку целостности;
- восстановление графа из проверенного снимка.

Граф является производным индексом и не заменяет единый источник истины (SSOT).

### Жизненный цикл и версии узлов графа

`tools/cks_graph_node_versioning.py` добавляет поверх существующего `KnowledgeGraph`, без создания второго графового движка:

- Graph Object Lifecycle (жизненный цикл узла графа) через общую машину состояний `cks_knowledge_state_machine.py`;
- Node Versioning (версионирование узлов), начиная с версии `1`;
- увеличение версии только при фактическом смысловом изменении;
- историю изменений каждого узла в служебном поле `_cks_node_versioning`;
- сохранение истории и версии через обычный JSON save/load графа;
- обязательную причину изменения;
- невозможность обойти защиту Canon через графовый слой: переход в `canonical` требует Evidence и Decision;
- защиту служебного поля истории от прямой перезаписи через публичный update-интерфейс.

## 6. Происхождение знаний

`tools/cks_traceability_engine.py` строит производные цепочки происхождения, включая отношения:

- `derived_from`;
- `evidenced_by`;
- `decided_by`;
- `implemented_by`;
- `reviewed_by`.

Движок сообщает о битых ссылках, но не создаёт решения и не повышает знания до Canon.

## 7. Представления знаний

CKS умеет строить производные представления:

- по статусам;
- по типам;
- по времени;
- по кластерам;
- по тегам;
- по Projects-проекциям;
- по связности;
- по проблемам;
- по происхождению;
- по уверенности и другим сигналам;
- в виде воронки `сырой материал → структурирование → знание → Canon/история`.

Цель — визуально показывать превращение входного информационного мусора в организованное знание.

## 8. Knowledge Intelligence — аналитика знаний

`tools/cks_knowledge_intelligence.py` реализует диагностическую аналитику:

- поиск кандидатов скрытых связей;
- предложения новых кластеров;
- анализ связности;
- поиск изолированных и слабосвязанных узлов;
- диагностику битых ссылок;
- явные конфликтные сигналы;
- анализ confidence / novelty / uncertainty / importance;
- анализ «что стало знанием»;
- карту развития Project;
- самоаудит качества знаний.

Результаты Intelligence имеют рекомендательный/диагностический характер и не являются Decision.

## 9. Obsidian

`tools/cks_obsidian_export.py` создаёт производную Obsidian-проекцию прямо в Git-каталоге:

- Markdown-заметки объектов;
- YAML frontmatter;
- wiki-ссылки;
- индексы `Кластеры/`, `Теги/`, `Проекты/`, `Статусы/`;
- обзор базы;
- `Карты/CKS_Граф.canvas` для графического представления.

Obsidian — визуальный слой. Он не является SSOT, Decision-механизмом или способом автоматического изменения Canon.

## 10. Федерация знаний нескольких проектов

`tools/cks_knowledge_federation.py` поддерживает:

- namespace (пространство имён) проекта;
- одинаковые локальные ID в разных проектах без коллизии;
- межпроектные связи;
- производный федеративный индекс;
- сохранение независимого владельца Canon каждого проекта.

Федерация объединяет навигацию и связи, но не объединяет Canon проектов.

## 11. Самопроверка и управление

`tools/cks_self_audit.py` проверяет:

- обязательные элементы репозитория;
- Control Plane (управляющий слой);
- реестр SSOT;
- языковую политику;
- модель объекта знания;
- синтаксис рабочего Python-кода;
- фактический runtime-контракт графа, трассировки, знаний и аналитики.

`tools/cks_governance_runner.py` объединяет проверки архитектурного управления.

Проверки имеют статус `diagnostic_only` / `validation_only` и не создают Canon.

## 12. Русский язык

Русский язык является основным человеческим языком CKS для:

- архитектурной документации;
- правил;

Английский сохраняется там, где нужен для кода, API, имён полей, форматов и совместимости. Технические термины в документации сопровождаются русским смыслом.
