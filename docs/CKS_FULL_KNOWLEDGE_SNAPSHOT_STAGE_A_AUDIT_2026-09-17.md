## Метод

Проверены фактические файлы текущей ветки `main`, а не только прежние сообщения чата. Цель — разделить требования на:

- `РЕАЛИЗОВАНО` — есть исполняемый код/схема и тестовый контур;
- `ЧАСТИЧНО` — часть модели существует, но отсутствует самостоятельный законченный механизм;
- `ДОКУМЕНТИРОВАНО` — требование записано, но полноценное исполнение не подтверждено;
- `ОТСУТСТВУЕТ` — не найдено.

## 2. Требования к развитию графа

| Требование | Статус | Вывод |
|---|---|---|
| Graph Object Lifecycle — жизненный цикл объектов графа | РЕАЛИЗОВАНО для объектов знаний | Схема `cks-knowledge-object.schema.json`, машина состояний и runtime содержат подробный жизненный цикл |
| Node Versioning — версии узлов | ЧАСТИЧНО | Объект знания имеет `version` и историю версий; `cks_knowledge_evolution.py` умеет создавать новую версию при переходе. Сам `KnowledgeGraph` не хранит отдельный журнал версий узла как часть графового хранилища |
| Relation History — история связей | ЧАСТИЧНО | Схема объекта разрешает `relations[].history`, `created_at`, `updated_at`, evidence/confidence; но рабочий `KnowledgeGraph.add_edge()` хранит связь как текущее состояние без отдельного versioned relation log |
| Graph Migration Engine — миграция формата графа | ОТСУТСТВУЕТ как самостоятельный механизм | Есть миграция объектов знаний в `cks_knowledge_evolution.py`, но нет мигратора `schema_version` самого графового JSON |
| Graph Recovery System — восстановление графа | ЧАСТИЧНО | Граф имеет атомарный `save/load`; объекты знаний имеют SHA-256 snapshot/recovery. Отдельный recovery-журнал/снимки именно графового хранилища не реализованы |

Это три главных технических разрыва Этапа B: Relation History, Graph Migration, Graph Recovery.

| Требование | Статус | Фактическое основание |

| Много представлений знаний | РЕАЛИЗОВАНО | `tools/cks_dynamic_views.py`: время, связность, проблемы, происхождение, воронка знания, проекты-проекции + базовые индексы runtime |

| Динамически видно превращение сырья в знания | РЕАЛИЗОВАНО | `knowledge_funnel()` / `воронка_материал_в_знание`, путь статусов и Obsidian Canvas |

## 4. Русский язык

**Статус: РЕАЛИЗОВАНО как принятое архитектурное правило.**

`docs/ADR-007_Двуязычная_модель_документации_CKS.md` устанавливает:

- русский язык — основной человеческий язык архитектурной документации, правил, требований и пользовательского взаимодействия;
- английский сохраняется для технических идентификаторов, API, YAML/JSON полей, кода и совместимости;
- английские технические термины должны иметь русское объяснение;
- единый терминологический источник — `docs/ГЛОССАРИЙ.md`.

Это правило также подтверждено в `ADR-0002`.

## 5. Obsidian

**Статус: РЕАЛИЗОВАНО.**

`tools/cks_obsidian_export.py` умеет создавать внутри указанного каталога/Vault:

- Markdown-объекты;
- YAML frontmatter;
- wiki-ссылки;
- отдельные индексы `Кластеры/`, `Теги/`, `Проекты/`, `Статусы/`;
- `Карты/CKS_Граф.canvas`;
- обзор пути от материала к знанию.

Каталог может находиться прямо в Git-репозитории. Obsidian остаётся производным визуальным слоем и не является SSOT или механизмом изменения Canon.

## 8. Что обнаружено при сверке документации

Корневые `README.md` и `ARCHITECTURE.md` корректно описывают замороженный baseline/Core `CKS_v1.2`, но сами по себе создают впечатление, что это и есть полное текущее состояние системы.

Одновременно `control/system-state.yaml` фиксирует:

- `current_version: CKS_v1.5`;
- baseline: `CKS_v1.2`;
- operational: `CKS_v1.3`;
- runtime: `CKS_v1.4`;
- development: `CKS_v1.5`;
- Core остаётся frozen, runtime — evolving.

Это не следует исправлять самовольным переписыванием v1.2 Canon. На Этапе C нужен отдельный постоянный русский Snapshot текущего рабочего состояния, который объясняет слои и не подменяет baseline.

## 9. Временные CI-отчёты

Workflow записывает `knowledge-runtime-self-audit.json` и `knowledge-runtime-governance.json`, но публикует их через `actions/upload-artifact`.

Следовательно, сам факт успешного CI сохранён в GitHub Actions, но итоговые JSON-отчёты не являются постоянными versioned-файлами репозитория. Это будет исправляться на Этапе C без коммита динамически меняющихся отчётов на каждый CI-run.

## Итог Этапа A

Инвентаризация показала, что основная знание-центричная архитектура, Runtime, Intelligence, Projects-проекции, русский слой и Obsidian уже реально существуют.

**Не закрыты три самостоятельных графовых механизма:**

1. versioned Relation History;
2. Graph Migration Engine;

Именно они являются следующим техническим этапом. Других функциональных дублей для них в текущем `main` не обнаружено.
