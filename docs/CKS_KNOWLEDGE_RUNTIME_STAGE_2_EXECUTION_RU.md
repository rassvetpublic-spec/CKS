# CKS Knowledge Runtime — этап 2

## Цель

Перевести модель объекта знания из описания в проверяемый рабочий контур без создания параллельной схемы.

## Что уже существовало до этапа

В репозитории уже были:

- `schemas/cks-knowledge-object.schema.json` — единая схема объекта знания;
- `tools/cks_knowledge_runtime.py` — нормализация, базовая проверка, индексы кластеров/тегов/статусов/проектов, динамические представления и экспорт в Obsidian;
- `validators/lifecycle_guard.py` — старый прототип проверки жизненного цикла;
- `control/lifecycle-state-model.yaml` — старый набор системных состояний.

Поэтому новый параллельный объектный Runtime не создавался.

## Реализовано

### 1. Машина состояний знаний

Добавлен `tools/cks_knowledge_state_machine.py`.

Она:

- проверяет допустимые переходы между статусами;
- блокирует прямой переход сырого материала в `canonical`;
- требует доказательство и ссылку на решение для перехода в `canonical`;
- считает `archived` и `rejected` терминальными состояниями;
- требует причину для обратного перехода;
- поддерживает старые `draft/review/active` как совместимые псевдонимы;
- ничего не изменяет автоматически.

### 2. Устранено расхождение двух жизненных циклов

Старый `validators/lifecycle_guard.py` проверял только:

`DISCOVERED → RESEARCHED → PROPOSED → REVIEWED → ACCEPTED → CANONICAL → DEPRECATED → ARCHIVED`.

При этом рабочий контур знаний уже использовал намного более детальные состояния от `raw` до `canonical`, `disputed`, `superseded` и `archived`.

Теперь старый API сохранён для системного жизненного цикла, а статусы знаний проверяются через единую машину состояний.

### 3. Control Plane уточнён

`control/lifecycle-state-model.yaml` теперь явно различает:

- системный жизненный цикл CKS;
- детальные статусы развития знания.

Источник списка статусов указан как существующая JSON Schema, а исполняемый валидатор переходов — как отдельный модуль.

### 4. Нормализация кластеров и тегов не продублирована

Существующий `KnowledgeRuntime.normalize()` уже:

- убирает пробелы по краям;
- удаляет точные дубли;
- приводит к спискам `clusters`, `tags`, `projects`;
- сортирует значения.

Поэтому второй нормализатор не создавался.

### 5. Добавлены тесты

`tests/test_cks_knowledge_runtime_stage2.py` проверяет:

- нормализацию кластеров, тегов и проектов;
- неизвестный статус;
- обычные переходы;
- запрет `raw → canonical`;
- требования доказательства и решения для канона;
- терминальный архив;
- обратный переход только с причиной;
- совместимость старых статусов;
- совместимость старого системного lifecycle API.

## Контроль предыдущих ошибок

На этом этапе специально применены ограничения:

1. Не создана вторая схема объекта знания.
2. Не объявлено, что наличие тестового файла означает успешный тестовый прогон.
3. Документ не считается реализацией: основное изменение — исполняемый Python-модуль и подключение валидатора.
4. Автоматическая проверка не является решением и не переводит объект в канон.
5. Документация написана на русском; английские идентификаторы оставлены только там, где они нужны машинному контракту и совместимости.

## Что ещё не проверено
