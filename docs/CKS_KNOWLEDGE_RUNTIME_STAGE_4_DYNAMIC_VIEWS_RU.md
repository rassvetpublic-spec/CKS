# CKS Knowledge Runtime — этап 4

## Цель

Сделать динамические представления реальной части рабочего контура знаний и явно показать путь «сырой материал → структурированное знание».

Статус документа: отчёт об исполнении. Документ сам по себе не является реализацией.

## Проверка предыдущего этапа

Перед реализацией этапа 4 повторно проверены:

- `tools/cks_knowledge_runtime.py`;
- `tools/cks_obsidian_export.py`;
- `tests/test_cks_obsidian_stage3.py`;
- существующий workflow `.github/workflows/cks-runtime-governance.yml`.

Обнаружена реальная проблема: workflow успешно выполнялся после этапа 3, но его интеграционный шаг запускал только `tests/test_cks_runtime_core.py`. Тесты этапов 2 и 3 существовали в репозитории, но не входили в основной runtime CI.

Это исправлено в рамках этапа 4: основной runtime CI теперь компилирует новые модули и запускает тесты этапов 2, 3 и 4 отдельно.

## Что реализовано

### 1. Динамический слой представлений

Добавлен `tools/cks_dynamic_views.py`.

Он использует существующий `KnowledgeRuntime` и не создаёт второй рабочий контур.

Формируются представления:

- по времени;
- по связности;
- по проблемам;
- по происхождению;
- воронка «материал → знание»;
- проекты как проекции графа знаний.

Базовые представления существующего Runtime сохраняются:

- по статусам;
- по типам;
- по кластерам;
- по тегам;
- по проектам;
- по уверенности.

## 2. Представление «материал → знание»

Рабочая воронка группирует объекты в стадии:

`вход → очистка → осмысление → знания → канон → история`.

Для каждой стадии выводятся:

- количество объектов;
- доля от общего числа;
- список идентификаторов.

Отдельно рассчитывается доля объектов, дошедших до знания или канона.

Эта метрика является диагностикой, а не решением о качестве проекта.

## 3. Представление по времени

История объектов собирается в:

- помесячный индекс;
- ленту событий;
- список объектов без даты.

Это позволяет визуально отслеживать не только текущее состояние, но и процесс превращения материала в знания.

## 4. Представление по связности

Узлы распределяются на:

- изолированные;
- слабосвязанные;
- связанные;
- узлы-хабы.

Считаются входящие и исходящие связи.

Классификация является производным представлением и не изменяет объект.

## 5. Представление проблем

Диагностируются:

- отсутствие кластеров;
- отсутствие тегов;
- отсутствие связей;
- зрелый объект без доказательств;
- оспариваемые объекты;
- битые ссылки на отсутствующие объекты.

## 6. Проекты как проекции

Для каждого проекта строятся:

- список объектов;
- распределение по статусам;
- распределение по кластерам.

Проект остаётся проекцией графа знаний и не становится контейнером файлов.

## 7. Обновлён контракт представлений

Расширена `schemas/cks-knowledge-view.schema.json`.

В контракт добавлены новые производные виды этапа 4. Источник истины не переносится в эту схему: она описывает только формат представлений.

## 8. Тесты

Добавлен `tests/test_cks_dynamic_views_stage4.py`.

Он проверяет:

- воронку «материал → знание»;
- связность;
- поиск классификационных пробелов;
- битые ссылки;
- временную шкалу;
- проекты-проекции;
- происхождение знания.

## 9. Исправление CI предыдущих этапов

`.github/workflows/cks-runtime-governance.yml` теперь:

1. компилирует Runtime, машину состояний, Obsidian-экспорт и динамические виды;
2. проверяет JSON-схемы;
3. запускает базовые runtime-тесты;
4. запускает тесты этапа 2;
5. запускает тесты этапа 3;
6. запускает тесты этапа 4;
7. выполняет самоаудит и управляющие проверки.

## Ограничения

- представление ≠ источник истины;
- граф ≠ канон;
- метрика ≠ решение;
- проблема, найденная автоматически, ≠ автоматическое исправление;
- Project (проект) = проекция графа знаний;
- документация и пользовательские подписи ведутся по-русски, технические идентификаторы сохраняются там, где они нужны совместимости.
