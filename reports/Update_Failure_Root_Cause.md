# SSOT-разбор первопричины: сбой обновления Windows 11 Insider 26220.9472

**Сформировано:** KAT9I_OS / Antigravity  
**Протокол:** SSOT Research Self-Audit Protocol v1.1  
**Цель:** база знаний CKS  
**QA-редакция:** подтверждённые факты отделены от причинных гипотез.

## 1. Исходное состояние и симптомы

### FACT
- Целевое обновление: Windows 11 Insider Preview 26220.9472.
- Обновление повторно откатывалось с ошибкой `0xC1900101`.
- Во время фазы SafeOS визуально наблюдался GSOD с `DPC_WATCHDOG_VIOLATION (0x133)`.
- Журналы установки содержали ошибку `Access Denied (0x00000005)`, связанную с миграцией компонентов Kaspersky.
- Изначально дампы были отключены (`CrashDumpEnabled=0`), поэтому визуально наблюдавшийся `0x133` не позволял установить первичный bugcheck (код критического сбоя) по дампу.

## 2. Методика и инструментирование

Для повторяемой проверки были включены:
- `CrashDumpEnabled=7` — Automatic Memory Dump (автоматический дамп памяти);
- `AlwaysKeepMemoryDump=1`.

Также был очищен кэш/остатки предыдущей попытки обновления и обновление повторно запущено для фиксации состояния отказа.

## 3. Финальные доказательства

В `C:\$WINDOWS.~BT\Sources\Rollback\setupact.log` после инструментированного повтора зафиксировано:

```text
Info  SP  Bugcheck code : 0x00000124
Info  SP  LastCrashDumpInfo: BugcheckCode 292
Info  SP  LastCrashDumpInfo: BugcheckParameter1 0
```

### FACT
- Bugcheck `0x124` (292) = `WHEA_UNCORRECTABLE_ERROR`.
- Parameter 1 = 0 указывает на Machine Check Exception (MCE, машинное исключение).
- Это подтверждает аппаратно зарегистрированное машинное исключение CPU-подсистемы во время SafeOS-нагрузки.

Ранее наблюдавшийся `0x133` следует считать визуальным симптомом одной из неудачных попыток, а не окончательно установленным первичным кодом данного инструментированного отказа.

## 4. Оценка первопричины

### VERIFIED FACT
Падение SafeOS, захваченное после включения диагностики, было вызвано `0x124 / MCE` при текущей CPU/BIOS-конфигурации под нагрузкой.

Перед последующей успешной попыткой были изменены параметры:
1. Enhanced Multi-Core Performance — отключён.
2. XMP — отключён.
3. CPU VCore — возвращён в Auto/Normal.

После этих изменений аппаратный `0x124` больше не сорвал обновление.

### VERIFIED — параллельный программный блокирующий фактор
В журналах отдельно присутствовал `0x00000005 Access Denied` при миграции Kaspersky. Перед финальной перезагрузкой пользователь временно отключил защиту Kaspersky; после этого программный блокирующий симптом не помешал завершению обновления.

### HYPOTHESIS — не повышать до FACT
Необратимая **silicon degradation (деградация кремния)** процессора этим инцидентом не доказана. Имеющиеся данные подтверждают нестабильность CPU-подсистемы при прежней конфигурации, но не позволяют различить:
- агрессивные BIOS-настройки;
- XMP/связанный контроллер памяти;
- напряжение/частоты;
- возрастную деградацию процессора;
- комбинацию этих факторов.

Поэтому `Silicon Degradation` сохраняется только как гипотеза для отдельной аппаратной проверки.

## 5. Применённое исправление

### Аппаратная часть / BIOS
- отключён Enhanced Multi-Core Performance;
- отключён XMP;
- CPU VCore возвращён в Auto/Normal.

### Программная часть
- защита Kaspersky временно отключена перед финальной перезагрузкой и стадией миграции обновления.

### Диагностика
- `CrashDumpEnabled=7`;
- `AlwaysKeepMemoryDump=1`.

## 6. Результат

### FACT
После указанных аппаратных и программных изменений обновление завершилось успешно; в исходном Antigravity-разборе конечная успешная сборка зафиксирована как `26220.9492`.

## 7. SSOT-вывод

Корректная причинная формулировка для CKS:

> Инцидент обновления содержал два независимых класса отказа: аппаратно зарегистрированный `0x124 / Machine Check Exception` под SafeOS-нагрузкой и программный `Access Denied` при миграции Kaspersky. Успех был достигнут после стабилизации BIOS/CPU-конфигурации и временного отключения защиты Kaspersky. Необратимая деградация кремния не доказана и остаётся гипотезой.
