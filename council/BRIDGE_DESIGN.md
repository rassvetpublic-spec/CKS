# CKS_BRIDGE — проект внешнего обмена, фаза 3

`Bridge` (посредник обмена) размещается вне CKS. Предлагаемая Windows-папка
задаётся переменной `CKS_BRIDGE_HOME`, например `C:\CKS_BRIDGE`:

```text
inbox/architect/
review/reviewer/
state/<repository>/<issue>/
logs/
config/
```

Предлагаемый стек: PowerShell 7, Python, GitHub CLI. Конкретные адаптеры Codex
и Antigravity подключаются только после проверки доступных интерфейсов.
Скрипта запуска, установленной службы и автоматического управления чатами в v0.1 нет.

## Алгоритм будущего обработчика

1. Получить структурированное предложение с ID репозитория/Issue, ревизией и SHA.
2. Зафиксировать событие во внешнем журнале; ключ дедупликации включает
   repository, issue, proposal_revision, event_id.
3. Сформировать задание Reviewer из краткого резюме, состояния и ссылок.
4. Проверить конверт результата, личность исполнителя и совпадение SHA/ревизии.
5. Вернуть замечания Architect либо подготовить решение владельца.
6. После трёх проверок остановить автоматический цикл. При отсутствии PASS
   APPROVE недоступен; возможны отклонение или новое связанное предложение.
7. Сохранить итоговые артефакты в CKS через обычную проверку изменений.

На один Issue допускается один писатель состояния. Запись через временный файл
и атомарную замену; после сбоя восстановление из журнала, повтор не создаёт
дублирующих заданий. История ревизий и причин отклонения сохраняется.
Метрики cycles_count, review_failures, decision_time, token_cost, rejected_patterns
хранятся снаружи; неизвестная стоимость — null, не ноль.

`.csk/context.json` — только возможный локальный, игнорируемый Git файл обмена.
Предпочтительно передавать путь к контексту в CKS_BRIDGE_HOME напрямую.
CORE не становится зависимым от IDE, очереди или постоянно работающей службы.
